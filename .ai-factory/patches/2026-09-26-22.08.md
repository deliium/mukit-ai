# Read-only piano-roll shortcuts still rewrote notes

**Date:** 2026-09-26 22:08
**Files:** frontend/src/components/PianoRollEditor.jsx, frontend/src/components/ComposerWorkspace.jsx, frontend/src/utils/collaborationAccess.js, frontend/src/utils/collaborationAccess.test.js
**Severity:** medium

## Problem

A commenter or viewer could cut, paste, delete, undo, nudge, and transpose notes from the piano-roll keyboard. Pointer creation was already blocked. The Collaborate tab list was also rebuilt on every render, which retriggered the tab-request effect.

## Root Cause

The read-only guard only covered pointer-down and the note `editable` flag. `handleEditorShortcut` still called the store mutation commands. The tab array was created inline, so its identity changed on every render even when `collaborationEnabled` did not.

## Solution

`isScoreMutationShortcut` lists the commands that rewrite note events. The piano roll returns before those commands when the role cannot `write_score`, and logs `[FIX]` with the command and role. Navigation, zoom, copy, and playback stay available. The tab list is memoized on `collaborationEnabled`.

## Prevention

- A read-only editor needs one gate for every input path that reaches a note mutation: pointer, drag, and keyboard.
- Keep the command list next to the role matrix and test it without mounting the piano roll.
- Memoize derived tab arrays that a `useEffect` reads.
