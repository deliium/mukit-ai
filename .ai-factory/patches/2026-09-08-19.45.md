# Attach MIDI/WAV projection response headers

**Date:** 2026-09-08 19:45
**Files:** backend/app/main.py, backend/tests/test_export_routes.py, frontend/e2e/v2-user-journey.spec.js, docs/composition-v2.md, scripts/v2_docker_acceptance.sh
**Severity:** medium

## Problem

`/aif-verify` against composition-v2 found Task 10 incomplete: MusicXML/preview returned `X-Mukit-Projection-*` headers, but `/export/midi` and `/export/wav` only set `Content-Disposition`. Frontend ExportControls already parse projection headers and append warnings, so MIDI/WAV approximations never appeared in the UI. The V2 e2e journey accepted bare `Downloaded` text as success.

## Root Cause

MIDI/WAV renderers already produced `ProjectionReport` via `render_midi_with_report` / `render_wav_with_report`, but the HTTP handlers still called the bytes-only wrappers and skipped `projection_response_headers`. Docs claimed all export routes attached headers before the wiring existed. Acceptance assertions were softened to `|Downloaded`, masking the missing warning path.

## Solution

- Switch MIDI/WAV routes to `render_*_with_report`, merge projection headers with Content-Disposition, and log issue counts/codes (never payloads) on INFO/WARNING.
- Add route tests for expressive MIDI headers and mocked WAV headers; update WAV monkeypatches to `render_wav_with_report`.
- Tighten Playwright assertions to require `Projection <code>` (or MusicXML automation omission), including after MIDI download.
- Clarify Consumers docs and extend `v2_docker_acceptance.sh` to assert MIDI projection headers.

## Prevention

- When adding a `*_with_report` renderer, require matching HTTP header attachment and a route test that reads `X-Mukit-Projection-*`.
- Do not accept generic success UI copy (`Downloaded`) as proof that projection warnings surfaced.
- Keep docs and docker acceptance scripts aligned with the three download formats, not MusicXML-only.
