# Coerce plan_form instrumentation objects to family strings

**Date:** 2026-09-07 20:27
**Files:** backend/app/services/composition_planner.py, backend/app/services/llm_music_generator.py, backend/tests/test_composer_form_instrumentation.py
**Severity:** high

## Problem

Staged generation failed at `plan_form` with:

```
LLM stage 'plan_form' returned invalid JSON: 3 validation errors for ComposerFormPlan
instrumentation.0 Input should be a valid string
[type=string_type, input_value={'family': 'piano', 'role': 'melody'}, input_type=dict]
```

DeepSeek (and similar models) returned instrumentation as objects with `family`/`role` instead of a string list, causing retries then a 502 on `/llm/generate-music-json`.

## Root Cause

`ComposerFormPlan.instrumentation` was typed as `list[str]` with no coercion. The form-stage prompt also said instrumentation must cover families "using melody, bass, and accompaniment roles", which nudged models to emit `{family, role}` objects. Roles belong to later compose stages; form instrumentation is only a family-string list.

## Solution

- Added `coerce_instrumentation_labels()` and a `mode="before"` validator on `ComposerFormPlan.instrumentation` that extracts `family`/`instrument`/`name` from object entries, dedupes case-insensitively, and preserves order.
- `_parse_form_plan` logs `[FIX]` when non-string entries are coerced before validation.
- Clarified the form prompt: instrumentation must be a JSON array of family strings only; roles are assigned later.

## Prevention

- Keep LLM stage schemas tolerant of common shape drift when the semantic mapping is unambiguous.
- Prompt examples and rules for list-of-string fields must not mention nested role fields.
- Regression tests should cover object-shaped instrumentation for piano/bass/violin-style requests.
