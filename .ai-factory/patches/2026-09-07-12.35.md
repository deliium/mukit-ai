# Assemble failed on duplicate LLM track IDs

**Date:** 2026-09-07 12:35
**Files:** backend/app/services/llm_music_generator.py, backend/tests/test_llm_staged_composer.py
**Severity:** high

## Problem

Staged generation completed form → harmony → melody → bass → accompaniment, then
failed at assemble with `Track IDs must be unique`. Soft-fail routed repair to
`assemble_composition` (no LLM rematch of drafts), so the same collision
exhausted the repair budget and returned HTTP 502.

## Root Cause

`_draft_to_track` kept each draft's LLM `id` as-is. Cross-stage collisions
(e.g. accompaniment reusing `melody-1`) and intra-accompaniment duplicates were
allowed by loose draft models and never remapped at merge. Uniqueness is only
enforced by canonical `Composition`, so assemble failed. Repair inference for
that message targets `assemble_composition`, which cannot rewrite draft IDs.

## Solution

1. Allocate unique track IDs while merging drafts (`_allocate_unique_track_id`),
   keeping the preferred ID when free and remapping collisions with
   instrument/index fallbacks and numeric suffixes.
2. Log remaps with `[FIX] Remapped duplicate assemble track id`.
3. Tell the accompaniment prompt which melody/bass IDs are reserved and require
   unique IDs in that stage.
4. Add regression test `test_assemble_remaps_duplicate_track_ids`.

## Prevention

- Treat track-ID uniqueness as an assemble/merge concern, not an LLM-only
  contract; always dedupe before constructing `Composition`.
- Do not route uniqueness failures to a non-LLM assemble repair loop without a
  remapping step.
- Keep a staged-composer test that injects colliding draft IDs across stages.
