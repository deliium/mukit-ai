# Disable LangChain TCP keepalive that drops slow DeepSeek bodies

**Date:** 2026-09-14 23:03
**Files:** backend/app/services/llm_chat_client.py, backend/app/services/llm_music_generator.py, backend/tests/test_llm_chat_client.py, frontend/vite.config.js
**Severity:** high

## Problem

After raising `LLM_REQUEST_TIMEOUT_SECONDS` to 180 and disabling SDK retries, generation still failed at ~60s:

```
LLM provider request failed during stage 'plan_form': APIConnectionError
```

Timeline: DeepSeek returned HTTP 200 headers, then exactly ~60s later the provider call failed (no SDK retries).

## Root Cause

`langchain_openai` injects Linux TCP socket options by default, including `TCP_KEEPIDLE=60`. Non-streaming chat completions often remain silent on the socket after response headers until the full JSON body arrives. Keepalive probes during that idle window can tear down a healthy slow connection, surfacing as `APIConnectionError` rather than `APITimeoutError`.

The earlier 60s `APITimeoutError` was the app timeout; once that was raised, the keepalive profile became the next 60s failure mode.

## Solution

- Pass `http_socket_options=()` into shared `build_chat_openai()` so LangChain skips the keepalive / `TCP_USER_TIMEOUT` profile; wait bound is solely `timeout_seconds`.
- Log client build at INFO with `timeout_seconds` and `http_socket_options_disabled`.
- Include `timeout_seconds=…` in the generation error message for visible diagnosis at LOG_LEVEL=INFO.
- Extend Vite `/llm`, `/motifs`, `/harmony`, and `/composition` proxy `timeout` / `proxyTimeout` to 300s so the browser proxy does not abort long provider waits.

## Prevention

- Prefer empty `http_socket_options` for non-streaming LLM clients unless a hang-detection profile is intentionally required.
- When diagnosing “HTTP 200 then fail at 60s”, distinguish app timeout (`APITimeoutError`) from idle TCP keepalive drops (`APIConnectionError`).
