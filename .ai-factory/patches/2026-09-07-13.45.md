# Integrity repair skipped after stage-parse retry; bass/strings thresholds too strict

**Date:** 2026-09-07 13:45
**Files:** backend/app/services/llm_music_generator.py, backend/app/services/composition_validator.py, backend/tests/test_llm_staged_composer.py, backend/tests/test_composition_validator.py
**Severity:** high

## Problem

After a successful assemble, integrity failed with sparse bass (22 events / 20 bars)
and strings pitches E2–B2 “outside practical range”. Logs showed
`Repair budget exhausted` with no `Composer repair attempt started`. An earlier
accompaniment stage parse failure had already burned `max_retries` (default 1).

## Root Cause

1. Outer stage-parse retries and in-graph integrity repairs shared `retry_count`.
   One accompaniment JSON failure incremented it to 1; the restarted graph then
   hit integrity errors and `_route_after_validation` treated the budget as spent.
2. `INSTRUMENT_PITCH_RANGES["strings"]` / pad role bottoms were C3, rejecting
   legitimate cello-register ensemble writing (E2, F2, A2, B2).
3. Bass density used the same complexity multiplier as melody (complex → 1.5/bar),
   which rejects musically normal sustained bass lines.

## Solution

1. Track stage-parse retries in `stage_retry_count` only; keep `retry_count` for
   integrity repair. Log `[FIX] Preserved integrity repair budget after stage parse retry`.
2. Widen strings/pad practical range to C2–C7.
3. Soften bass min-events to at most `0.5 * bar_count`.
4. Prompt notes for strings range; regression tests for budget separation, cello
   register, and bass density.

## Prevention

- Never share one retry counter across full-graph parse restarts and targeted
  integrity repairs.
- Instrument ranges for generic “strings” must include cello lows.
- Density gates should be role-aware (bass sustains ≠ melody density).
