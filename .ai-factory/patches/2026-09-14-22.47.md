# Raise LLM request timeout and disable SDK transport retries

**Date:** 2026-09-14 22:47
**Files:** backend/app/services/llm_chat_client.py, backend/app/llm_settings.py, backend/app/services/llm_music_generator.py, backend/app/services/llm_composition_editor.py, backend/app/services/llm_motif_editor.py, backend/app/services/llm_composition_development.py, backend/app/services/llm_composition_arrangement.py, backend/tests/test_llm_chat_client.py, backend/tests/test_llm_settings.py, .env.example, README.md, docker-compose.yml
**Severity:** high

## Problem

`POST /llm/generate-music-json` failed during stage `plan_form` with:

```
LLM provider request failed during stage 'plan_form': APITimeoutError
```

Logs showed DeepSeek returning HTTP 200, then OpenAI SDK retries every ~60s, then a 502 after ~3 minutes.

## Root Cause

1. Default `LLM_REQUEST_TIMEOUT_SECONDS` was 60. DeepSeek often accepts the request (headers → 200) but needs longer than 60s to finish the completion body for staged composer prompts.
2. `ChatOpenAI` used the OpenAI SDK default `max_retries=2`, so one slow call became three sequential 60s waits before the app surfaced `APITimeoutError`.
3. Failure logs omitted `timeout_seconds`, which made the misconfiguration harder to diagnose.

App-level repair already owns retry budgets (`options.max_retries`); SDK transport retries were redundant and harmful for long LLM calls.

## Solution

- Raised default request timeout from 60 → 180 (still capped at 300 via env validation).
- Added `build_chat_openai()` shared factory that always sets `max_retries=0` and the configured timeout.
- Wired the factory into generation, region edit, motif, development, and arrangement provider calls.
- ERROR logs now include `timeout_seconds` and a `[FIX]` prefix on provider failures.

## Prevention

- Build all LangChain OpenAI clients through `llm_chat_client.build_chat_openai` — do not construct `ChatOpenAI` inline with default SDK retries.
- When diagnosing LLM 502s, check whether HTTP 200 precedes a timeout: that pattern is body-read timeout, not connection failure.
- Keep app-level repair retries separate from transport retries.
