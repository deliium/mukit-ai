# Socket close 1013 when the adaptive engine events queue is full

**Date:** 2026-09-29 23:51
**Files:** backend/app/services/adaptive_engine_service.py, backend/app/routers/adaptive_engine.py, backend/tests/test_adaptive_engine_api.py, docs/adaptive-music-engine.md
**Severity:** medium

## Problem

When `WS /adaptive/events` already held `ADAPTIVE_ENGINE_EVENT_QUEUE` acknowledgements, the next acknowledgement was dropped and the socket stayed open. Decision 7 requires close code `1013` in that case, after queued acknowledgements and errors are kept.

## Root Cause

`_put_now` tried to enqueue a `close` frame only when `Queue.full()` was already false. A queue full of non-status frames has no free slot, so the close frame was skipped and the function returned. The reader only closes when it dequeues a `close` frame, so it never saw `1013`.

## Solution

Record `close_code` on the feed when an acknowledgement or error cannot be queued. Do not remove the frames already in the queue. Status frames are still the ones dropped to make room. The socket loop sends the queued frames, then closes with that code when the queue is empty. The overflow is logged with prefix `[FIX]`, the frame kind, and `close_code`. The frame body is not logged.

## Prevention

A bounded outbound queue needs a close signal that does not itself require a free slot. Review websocket caps by filling the queue with the undroppable frame type and asserting both the kept frame and the close code. Status frames are the only kind that may be replaced.
