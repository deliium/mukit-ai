# Accept single-accidental enharmonics in pitch→MIDI maps

**Date:** 2026-09-15 11:45
**Files:** backend/app/composition_schemas.py, backend/app/services/composition_tonality.py, frontend/src/utils/musicJsonValidation.js, frontend/src/utils/pianoRollEvents.js, backend/tests/test_composition_schema.py, backend/tests/test_llm_staged_composer.py, frontend/src/utils/pianoRollEvents.test.js
**Severity:** high

## Problem

LLM stage `compose_melody` failed with:
`LLM stage 'compose_melody' returned invalid JSON: KeyError: KeyError('E#')`

The model returned scientific pitches like `E#4` (common in sharp keys). Pitch regex accepted them, but `NOTE_TO_SEMITONE` lacked `E#`/`B#`/`Fb`/`Cb`, so `midi_pitch_number` raised `KeyError`. Stage handlers catch `KeyError` as “invalid JSON”.

## Root Cause

`NOTE_PITCH_PATTERN` / `COMPOSITION_PITCH_PATTERN` allow any `[A-G][#b]?` spelling, but the backend and frontend semitone tables only listed the “common” twelve spellings. Validators caught only `ValueError`, so the `KeyError` escaped pydantic and was mislabeled as bad JSON. `B#`/`Cb` also need octave-crossing offsets (`12` / `-1`), not plain pitch-class values.

## Solution

- Extended `NOTE_TO_SEMITONE` (backend + frontend) with `E#`, `Fb`, `B#`, `Cb` using octave-correct offsets.
- Made `midi_pitch_number` convert unknown spellings to `ValueError` with `[FIX]` logging instead of raw `KeyError`.
- Extended tonality `_NOTE_NAME_TO_PC` for the same tokens.
- Added schema/composer/piano-roll regression coverage.

## Prevention

- Keep pitch regex and `NOTE_TO_SEMITONE` complete for every single-accidental letter the pattern allows.
- Prefer `ValueError` (not `KeyError`) from pitch helpers so LLM stages surface musical validation failures clearly.
- Add parametrized tests for enharmonics whenever pitch maps change; mirror backend and frontend maps together.
